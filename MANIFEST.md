# CascadePort MANIFEST

What exactly is in this repo, how it was proven, and what the Xcode
project must replicate. Generated by hand from the build records;
counts are exact.

## Architecture principle

**Swift drives; Cascade does the geometry.**

After this port, everything above the façade is Swift, and Swift
calls everything from the actual OCCT libraries. The façade
(`Facade/occt_facade.h` / `.cpp`) is a **thin, complete
pass-through**: it exposes OCCT's own operations as direct C-ABI
wrappers — primitives, prism, revolve, loft, sweep, booleans,
fillet, chamfer, shell/offset, tessellation with per-face ranges,
volume / bounding-box / contains queries, and (added 2026-10-27,
see "Sketch support" below) sketch faces built from line / circle
/ arc entities with holes, a face prism, and a face-area query.
Also added 2026-10-27 (see "Selection / query layer" below): a
shape census (face / edge / vertex counts plus per-face and
per-edge info) in the same index space the finishing functions
already consumed. It implements **no CAD
feature logic and no geometry math of its own**: the C++ side only
translates calls and data (handles in, buffers out) and catches
OCCT exceptions at the boundary. Where OCCT has an operation, the
façade wraps it rather than approximating it — e.g. fillets are
`BRepFilletAPI_MakeFillet` (true rolling-ball blends), shell is
`BRepOffsetAPI_MakeThickSolid` (true offset), booleans are
`BRepAlgoAPI_*`.

**Library form (2026-10-27).** The façade is now presented as
what it is: the public C API of the **CascadeKit** geometry
library (the static-library target the apps link). The public
header `Facade/occt_facade.h` is organised in eleven documented
sections — 1 handles/errors/lifecycle, 2 primitives, 3 profiles,
4 sketches, 5 booleans, 6 finishing, 7 queries, 8 selection
census, 9 tessellation, 10 import/export, 11 FEM — with the
library's conventions (units, error model, ownership, shared
index spaces) stated at the top. No existing signature changed
through section 10. Section 10 (see "STEP import" below) added
`mc_import_step` / `mc_export_step`, and the app uses it — an
imported STEP file becomes the app's *current body*, and the
sketch editor's Finish & Extrude can then unite the extrusion
into the body or cut it out (the booleans of section 5, applied
by the app). Section 11 (see "FEM" below) is the one section
that is NOT a pass-through: the project's own voxel mesher and
linear-static solver, standing on OCCT geometry queries.

The TKDE/TKXSBase/TKDESTEP rows are the **STEP import expansion**
(2026-10-27), derived the same way as the original subset: the
transitive `EXTERNLIB.cmake` closure of the toolkit that holds
the STEP reader/writer (`STEPControl_Reader` / `STEPControl_Writer`
live in **TKDESTEP** in OCCT 8.0.1). That closure names 11
further toolkits, and they split by what they serve:

- **The shape path** — TKDESTEP, TKDE, TKXSBase (above): everything
  `STEPControl_Reader` compiles and links against.
- **The document path** — TKCDF, TKLCAF, TKCAF, TKXCAF, TKVCAF,
  TKService, TKV3d, TKHLR: these enter the closure only because
  TKDESTEP also ships OCCT's *XDE document* packages
  (STEPCAFControl, and the DE-plugin provider pair in DESTEP),
  which read STEP into an XCAF document (names, colours, assembly
  structure). That branch was pruned in the STEP phase (façade
  imported geometry only) and **restored 2026-10-28 for STEP
  surface colours** — the façade now also reads each imported
  file through `STEPCAFControl_Reader` + `XCAFDoc_ColorTool` and
  exposes per-face colours (`mc_shape_face_colors`), so the
  branch toolkits the colour path actually needs are in: TKCDF,
  TKLCAF, TKCAF, TKXCAF, and TKService pruned to its five data
  packages (Aspect, Graphic3d, Image, Font, Media — pulled in by
  `XCAFDoc_VisMaterial` / `STEPConstruct_RenderingProperties`;
  excluded: Shaders viewer GLSL texts and the Xw/WNT/Cocoa/Wasm
  platform window backends, which no shipped source references).
  Inside the branch the pruning is exact and verified by include
  scan: TKVCAF is NOT added (its sole package is TPrsStd, the AIS
  presentation driver table — display glue nothing in the colour
  path references), TKV3d/TKHLR are not added (AIS viewer /
  hidden-line; the module-level closure over-approximates —
  TKDESTEP's own EXTERNLIB names only TKCDF/TKLCAF/TKCAF/TKXCAF
  beyond the shape path), package XCAFApp is excluded (its single
  class registers an AIS presentation driver in its constructor;
  the façade creates documents directly with
  `new TDocStd_Document`), and package XCAFPrs is pruned to its
  base file + the Style/Texture data classes (`AISObject` /
  `Driver` / `DocumentExplorer` are viewer machinery). Inside
  TKDESTEP the restoration is the mirror of the earlier prune:
  STEPCAFControl ships whole, DESTEP ships whole (was reduced to
  `DESTEP_Parameters`), and STEPConstruct's `Styles` +
  `RenderingProperties` are restored (STEPCAFControl_Reader /
  Writer use both).

Per-package file selection follows OCCT's own package
`FILES.cmake` lists, plus the package directories' inline include
files (`.lxx` / `.pxx` / `.gxx`) that OCCT collects by glob — the
same set OCCT's cmake build compiles. `GTests` directories (unit
tests, need GoogleTest) are excluded. Totals (original 15
toolkits + the STEP expansion's 3 + the XDE restoration's 5):

- **4,270 `.cxx` + 1 `.cpp` + 1 `.c` = 4,272 compilable OCCT sources**
  (the `.cpp` is `BRepMesh/delabella.cpp`, the triangulator bundled
  inside OCCT's TKMesh; the `.c` is TKernel's
  `Resource_ConvertUnicode.c`)
- **5,535 header files** in `OCCT/src` (`.hxx/.lxx/.pxx/.gxx/.h`)
- **1 generated header**: `OCCT/generated/Standard_Version.hxx` —
  the only header OCCT generates (from `adm/templates/
  Standard_Version.hxx.in`); the copy shipped here is the exact
  file OCCT's cmake produced for 8.0.1.
- `OCCT/` total: **9,807 files, ~91 MB**.

Excluded modules/toolkits, and why: the ApplicationFramework /
Visualization toolkits outside the XDE colour branch discussed
above (TKVCAF, TKV3d, TKHLR and the rest), the rest of Data
Exchange (IGES — TKDEIGES; glTF/OBJ/PLY/STL/VRML — TKDEGLTF,
TKDEOBJ, TKDEPLY, TKDESTL, TKDEVRML; RWMesh — TKRWMesh), Draw, plus the
ModelingAlgorithms toolkits nothing in the closure needs: TKHLR
(drawing hidden-line removal — only reachable via the document
branch), TKFeat (feature recognition helpers), TKExpress (schema
codegen runtime), TKHelix (OCCT 8's new helical-sweep toolkit —
not needed: threads in MetalCAD are profile sweeps, which
`mc_sweep` covers), TKXMesh (XDE mesh exchange). If a future
façade operation needs one, add its toolkit and its EXTERNLIB
closure the same way.

Façade/driver compile flags (what the Xcode project replicates):
`-std=gnu++17 -fexceptions -frtti -DNDEBUG -DNo_Exception

`TKOffset TKFillet TKBO TKMesh TKPrim TKBool TKTopAlgo
TKShHealing TKGeomAlgo TKBRep TKGeomBase TKG3d TKG2d TKMath
TKernel`, plus `-lpthread -ldl` (Linux-only; iOS needs neither —
libc++ is linked into the app via `OTHER_LDFLAGS = -lc++`).

Notes from the proof:
- **Circular toolkit references**: TKBool and TKBO reference each
  other (e.g. TKBool's `BRepAlgo_NormalProjection` uses TKBO's
  `BRepAlgoAPI_Section`), so the Linux link wraps the 15 archives
  in `-Wl,--start-group … --end-group`. In the Xcode project all
  objects land in ONE archive (`libCascadeKit.a`) and ld64 rescans
  within a single archive, so no equivalent setting is needed.
- **OCCT 8 API differences** the façade already accounts for
  (found by compiling against the real 8.0.1 headers):
  `TopTools_IndexedMapOfShape` no longer exists — the type is
  `NCollection_IndexedMap<TopoDS_Shape, TopTools_ShapeMapHasher>`;
  symmetric chamfer is `BRepFilletAPI_MakeChamfer::Add(distance,
  edge)` (the old two-distance overload is gone);
  `BRepBndLib::Add` inflates the box by triangulation gap, so
  `mc_bbox` uses `BRepBndLib::AddOptimal` (exact geometry bounds).
- **Shell semantics** (read from the 8.0.1 sources,
  `BRepOffset_MakeOffset::MakeThickSolid`): with an empty
  removed-faces list, `MakeThickSolidByJoin` returns the bare
  inward-offset solid, not the hollow part. `mc_shell` therefore
  composes two OCCT operations — that offset, cut from the original
  with `BRepAlgoAPI_Cut` — both library operations; the façade
  still computes no geometry itself. Result verified: 20×20×10 box,
  1.5 mm walls → exactly 1977 mm³ (4000 − 17×17×7).
- OCCT is built **without TBB** (not present; OCCT parallelises
  internally where compiled in, and every façade call is correct
  single-threaded). TKBO's EXTERNLIB mentions `CSF_TBB` — optional,
  absent here exactly as in OCCT's own no-TBB configuration.
- No resource files are needed at runtime by any façade operation
  (no `CSF_*` environment paths are consulted by these toolkits for
  these calls). This was exercised by the proof run in a bare
  environment.

## Sketch support (added 2026-10-27)

Sean's follow-on ask: sketching must go through Cascade too. Three
façade functions were added; the 20 proof checks below were run
with the same harness (whole suite now **77 checks, ALL PASS** —
the original 57 unchanged):

- `mc_face_from_sketch(origin, normal, xDir, entityTypes,
  entityData, entityCount, profileStarts, profileCount, err)` —
  the sketch plane is a `gp_Pln` (from `gp_Ax3`: origin, normal,
  xDir); each entity becomes a real OCCT curve/edge: lines via
  `GC_MakeSegment`, arcs via `GC_MakeArcOfCircle` on a `gp_Circ`,
  circles as a `gp_Circ` edge, all through
  `BRepBuilderAPI_MakeEdge`; profiles become wires through
  `BRepBuilderAPI_MakeWire` and the face through
  `BRepBuilderAPI_MakeFace(plane, outerWire)` + `Add(holeWire)`.
  Entities arrive as parallel arrays — a type array plus a flat
  data array with a fixed stride of 6 doubles per entity (line:
  x1,y1,x2,y2; circle: cx,cy,r; arc: cx,cy,r,start,end radians
  CCW) — and profiles as CSR ranges (`profileStarts`, count+1
  entries); profile 0 is the outer profile, the rest are holes.
  The result is validated with `BRepCheck_Analyzer` before it is
  handed back, so a bad sketch is an error code, never a bogus
  face.
- `mc_prism_face(face, dir, dist, err)` — `BRepPrimAPI_MakePrism`
  of a face handle (the sketch counterpart of the polygon-only
  `mc_prism`, which stays).
- `mc_face_area(shape, err)` — face area via
  `BRepGProp::SurfaceProperties` (that is OCCT 8.0.1's name for
  the face-properties entry point; its Mass() is the area).

Design note — where the façade's work begins and ends: the plane,
the entities, the wires and the face are OCCT `gp` / `Geom` /
`BRep` objects end to end; **no profile math lives in the
façade**. The only sequencing the façade performs is ordering
each profile's entities end to end (endpoint match within
1e-6 mm) because `BRepBuilderAPI_MakeWire` requires connected
input, plus two pieces of pure representation translation, both
verified empirically against 8.0.1:

- **Hole wires are reversed before `Add`.** OCCT represents a
  hole by a wire oriented opposite to the outer wire, and
  `MakeFace::Add` does not reorient: an unreversed circular hole
  in the proof's 40×40 plate produced area **1678.540** (the hole
  ADDED as material) and failed `BRepCheck`; reversed, the same
  input gives **1521.460** and a valid face. Callers describe
  every profile in the same orientation; the reversal is done
  inside.
- **Arc sweeps are normalised** to CCW from start to end
  (wrapping past 2π); a zero/full-turn sweep is rejected — a full
  circle is the circle entity's job.

## Selection / query layer (added 2026-10-27)

MetalCAD's selection-driven tools (Sean's rule: a tool opened
from a selection uses the selection's actual measurements) need
Swift to enumerate a shape's faces and edges, read their real
geometry, and hand edge indices back to the finishing functions.
Three façade functions were added; the 34 proof checks below were
run with the same harness (whole suite now **111 checks, ALL
PASS** — the original 77 unchanged):

- `mc_shape_counts(shape, *faces, *edges, *vertices, err)` —
  the census: `TopExp::MapShapes` extents for faces, edges,
  vertices.
- `mc_face_info(shape, faceIndex, *area, center[3], normal[3],
  *isPlanar, err)` — area + area centroid via
  `BRepGProp::SurfaceProperties`; planarity + outward normal via
  `BRepAdaptor_Surface` (plane axis, flipped when the face's
  stored orientation is reversed; for a non-planar face the
  normal is reported as (0, 0, 0)).
- `mc_edge_info(shape, edgeIndex, *curveType, *length,
  start[3], end[3], center[3], *radius, err)` — curve type
  (0 line / 1 circle / 2 other) via `BRepAdaptor_Curve`; length
  via `BRepGProp::LinearProperties` (OCCT 8.0.1 has no
  `BRepGProp::EdgeProperties` — LinearProperties is its name for
  the edge entry point, and its Mass() is the length); endpoints
  via `BRep_Tool::Pnt(TopExp::FirstVertex / LastVertex)`;
  circle centre / radius from the adaptor's `Circle()`.

**One index space, by construction.** Faces, edges and vertices
are enumerated in TopExp traversal order (each distinct
sub-shape at its first occurrence — the `TopExp::MapShapes`
enumeration that `mc_edge_count`, tessellation's per-face
ranges, and the finishing functions already used). The census
reads from the same maps, so an index Swift learns from
`mc_edge_info` names the same physical edge in `mc_fillet` —
the proof demonstrates this end to end: the length L0 of edge 0
is read through `mc_edge_info`, edge 0 alone is filleted
through the existing `mc_fillet`, and the resulting volume
matches the closed form for THAT edge to 0.001 mm³.

**No `mc_fillet_edges` / `mc_chamfer_edges` were added** —
`mc_fillet` / `mc_chamfer` already accept an edge index list
(NULL = all edges), implemented by the shared `edgeOp` over the
same map. The selective forms are proven below instead of
duplicated.

Findings from the proof, recorded exactly as measured:

- **Selective finishing is exact.** Box 20×20×10, edge 0
  (L0 = 10, read from the census): fillet r=2 on that edge only
  → volume **3991.416** = 4000 − (2² − π·2²/4)·10, and the
  result has exactly **7 faces**; chamfer d=1 on that edge only
  → **3995.000** = 4000 − (1²/2)·10. Bad indices (face 999,
  edge 999, fillet list {999}) return `MC_ERR_INVALID_ARG`,
  never a crash.
- **The filleted box's true census is 26 / 56 / 24** (faces /
  edges / vertices) — NOT the 72 edges / 48 vertices an earlier
  draft of the test expected. Composition: 6 planar faces
  (areas 256 ×2, 96 ×4) + 12 cylindrical fillet strips (areas
  50.265 ×8 along the 20 mm edges, 18.850 ×4 along the 10 mm
  edges) + 8 spherical corner patches (area 2π each); edges
  are 24 tangent lines + 24 quarter-circle arcs (r=2, length
  π) + **8 degenerate pole edges** (length 0, start == end) —
  one per spherical patch, an artefact of the sphere
  parametrization (each patch is a trimmed sphere face whose
  wire carries a pole edge), not a cell of the decomposition.
  Euler therefore holds on the true cells: V − (E − 8) + F =
  24 − 48 + 26 = **2**. Swift should treat a curveType-2,
  zero-length edge as a pole artefact, not a selectable edge.
- Box census is 6 / 12 / 8 with Euler exact; all 12 edges are
  lines whose lengths sum to exactly 200; all 6 faces are
  planar with areas {200, 200, 200, 200, 400, 400}, and the
  +Z face reports centre (10, 10, 10) and normal (0, 0, 1) —
  the outward-normal orientation convention (reverse on
  `TopAbs_REVERSED`) confirmed empirically on all 6 faces.

## FEM — mesh + basic stress analysis (added 2026-10-27)

Library section 11 (`mc_fem_*`, in `Facade/occt_facade.h` /
`.cpp`) is Sean's FEM commission: pick faces to fix, apply a
force, see von Mises stress. It is the project's **own**
numerical code — the architecture principle above applies to
sections 1–10; here OCCT supplies only the geometry queries
(`BRepClass3d_SolidClassifier` for inside tests,
`BRepExtrema_DistShapeShape` for point-to-face distance, the
census for face indices). Nothing under `OCCT/` changed; no new
OCCT toolkit was needed.

Method, as implemented:

- **Voxel mesh** (`mc_fem_mesh`): uniform grid over the shape's
  optimal bounding box; a cell is kept when its CENTRE classifies
  inside a solid of the shape. Kept cells are hex8 elements on a
  shared structured node grid. Element cap 250,000
  (`MC_FEM_MAX_ELEMENTS`); the classification scan itself is
  capped at 8,000,000 cells so an absurd voxel size fails fast.
  The mesh also exposes its boundary quads, each associated with
  the census face nearest its centre (or −1), and its realised
  volume (elements × h³) so callers can warn on drift against
  the solid's true volume.
- **Face mapping** (`mc_fem_nodes_on_face`): surface nodes
  whose point-to-face distance is below 0.75 × voxel size
  (cached per face). Fixity and loads are expressed through
  these sets; a face's total load spreads evenly over its
  mapped nodes.
- **Solve** (`mc_fem_solve`): hex8 trilinear stiffness, full
  2×2×2 Gauss integration — every element is the same cube, so
  one stiffness matrix serves the mesh (exact, not an
  approximation). Full assembly into compressed sparse row form
  (3×3 nodal blocks) over the free nodes; preconditioned
  conjugate gradients with a Jacobi preconditioner, relative
  tolerance 1e-8, iteration cap 10,000. **Convergence is gated
  on the recomputed residual** r = b − Ax (the recursive CG
  residual can drift, and on a singular-but-almost-consistent
  system it can fake convergence — found and fixed during this
  phase's proof: a one-node-clamped solve previously "passed";
  it now fails cleanly). No fixity, non-positive diagonal, or a
  CG breakdown returns `MC_ERR_FEM_SINGULAR`; exhausting the
  cap returns `MC_ERR_FEM_NO_CONVERGE`. Results: per-node
  displacements, per-element centroid von Mises, node-averaged
  von Mises, max von Mises (element centroid), max displacement,
  iterations, final true relative residual.

Proof (same host harness; whole suite now **190 checks, ALL
PASS** — the 127 of the earlier sections unchanged, plus 63 FEM
checks). The gate is the cantilever against beam theory at two
resolutions. Beam 100×10×10 mm, steel E = 200 000 MPa, ν = 0.3,
wall face clamped, 1000 N down on the end face. Analytic:
I = 833.33 mm⁴, δ = PL³/3EI = **2.000 mm**, σ_wall = Mc/I =
**600 MPa**.

| Case | FEM | Analytic | Error |
| --- | --- | --- | --- |
| δ tip, h = 2.5 (640 elem, 25 nodes/face) | 1.9355 mm | 2.000 | −3.2% |
| δ tip, h = 1.25 (5120 elem, 81 nodes/face) | 1.9882 mm | 2.000 | −0.6% |
| σ max, h = 2.5 | 415.78 MPa | 600 | −30.7% |
| σ max, h = 1.25 | 497.88 MPa | 600 | −17.0% |

δ converges to within 0.6%. σ is honestly rougher, as expected
of this method: the reported maximum is sampled at element
centroids, which sit h/2 away from the wall and h/2 inside the
outer fibre (at h = 1.25 the outer layer's centroid sits at
c = 4.375 of 5 mm, i.e. an exact field would already read 525
there), trilinear elements are stiff in bending, and the
clamped wall adds its own local effects. It improves
monotonically with refinement; it is a guide number, not a
certified peak stress.

Supporting checks, as measured: uniaxial tension (40×10×10,
10 000 N → P/A = 100 MPa): the 64 interior elements' centroid
von Mises deviate from 100 by **at most 0.13 MPa**, and the
loaded face's mean stretch is 0.020316 mm against the analytic
σL/E = 0.020000 (+1.6%, the clamped end's Saint-Venant layer).
Assembly symmetry verified directly by Maxwell–Betti
reciprocity: F·u agrees to the printed precision (six decimals)
between the two reciprocal load cases. A single clamped element
does NOT reproduce P/A (VM = 8.50 of 10): the clamped face's
nodes are held in all directions and cannot make the Poisson
contraction — the uniform field is not its discrete solution;
the test pins this explained behaviour, and the patch test
above is the exactness gate. Sanity: zero fixity →
`MC_ERR_FEM_SINGULAR`; one fixed node → clean FEM error (never
a result); a load placed only on the fixed face →
`MC_ERR_INVALID_ARG`; element cap and scan cap → clean errors.
The demo's holed plate at h = 2 (1 920 elements) meshes with
0.96% volume drift and solves in ~0.14 s on the host.

Host wall-times (2-core sandbox VM, indicative only): beam
h = 1.25 mesh 0.47 s / solve 0.30 s (331 iterations); beam
h = 2.5 solve 0.02 s; plate mesh 0.55 s / solve 0.14 s. Expect
device times of the same order for meshes of this size; at the
250 000-element cap the CSR matrix is several hundred MB and a
solve is a minutes-scale job — the app's Fine setting on a
typical part lands far below the cap.

App behaviour built on this (DemoApp, `FEM.swift`): with a
current body present, **FEM** opens the analysis panel over the
same 3D view. Faces are picked by tapping (SceneKit hit test →
triangle ordinal → the tessellation's per-face range → census
face index) and coloured in place: fixed blue, loaded orange.
Controls: Fix/Load mode, force per loaded face (N, stepper +
field), direction Push in / Pull out (along the face's outward
normal; non-planar faces use centre-outward), material presets
(PLA 3 500 MPa ν 0.36 · Aluminum 69 000 ν 0.33 · Steel
200 000 ν 0.30), mesh size Coarse/Medium/Fine (voxel = bbox max
dimension / 16 / 32 / 64) with the realised node/element counts
shown after meshing, and a plainly-worded warning when the mesh
volume drifts more than 5% from the solid's. Results re-colour
the voxel surface by node von Mises (blue → red, legend with
the maximum), with max von Mises, max displacement and solver
iterations in large type; Reset returns to the plain body.

Panel fixes (2026-10-28, from on-device use): (1) **Layout** —
the first panel let the 3D view claim the full proposed height
(`maxHeight .infinity` + `layoutPriority 1`), which laid the
whole control stack below the screen edge: on the device only
Fix/Unfix was reachable and the Load mode, force field, Mesh
and Solve controls could not be reached at all. The panel is
now pinned by a `GeometryReader` to its real height: the view
takes a bounded 54% share and every control lives in a
ScrollView that takes exactly the remaining height, in both
orientations. (2) **Picking** — the selection scene is built
once per body; a tap now recolours only the tapped face's
`SCNMaterial` diffuse in place (the whole scene — hundreds of
elements and materials — was rebuilt on every tap, which felt
janky). Hit testing is unchanged (SceneKit returns hits
nearest-first; the first hit's triangle ordinal maps through
the tessellation ranges to the census face). (3) The selection
view's per-face base colour is the face's STEP colour when the
import carried one (see "STEP colours via XDE").
Caption in the UI: "Basic linear stress analysis — voxel
mesh."

## Where iOS/Xcode may differ from the Linux proof (honest list)

The first true compile happens in Xcode on Sean's Mac. Known
classes of possible nits, in rough likelihood order:

1. **`__APPLE__` code paths** in OCCT sources that the Linux build
   never took (OSD / resource / signal handling in TKernel). They
   are standard Darwin paths OCCT ships for its own iOS sample, but
   they were not compiled here.
2. **A missing preprocessor define** that Darwin needs and Linux
   didn't (the define set above is exactly the one OCCT's cmake
   used on Linux; OCCT's iOS build script uses the same core set).
3. **Static-initialisation / resource-path behaviour**: OCCT
   registers some factories statically; none of the façade's
   operations needed resources on Linux, but an iOS sandbox path
   difference could surface as an OCCT exception — which the façade
   reports as an error code + message in the demo, not a crash.
4. **Clang vs GCC strictness**: a handful of OCCT files may warn
   (the project does not treat warnings as errors); a hard error
   would be a one-file patch.
5. **The demo's Info.plist** follows the hand-written pattern
   MetalCAD already runs with on-device (no scene manifest); if a
   future iOS demands one, it is a 6-line addition.

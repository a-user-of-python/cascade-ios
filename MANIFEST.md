# CascadePort MANIFEST

What exactly is in this repo, how it was proven, and what the Xcode
project must replicate. Generated by hand from the build records;
counts are exact.

## Architecture principle

**Swift drives; Cascade does the geometry.**

After this port, everything above the façade is Swift, and Swift
calls everything from the actual OCCT libraries. The façade
(`Facade/occt_facade.h` / `.cpp`) is a **thin, complete
pass-through**: it exposes OCCT's own operations as direct C-ABI
wrappers — primitives, prism, revolve, loft, sweep, booleans,
fillet, chamfer, shell/offset, tessellation with per-face ranges,
volume / bounding-box / contains queries, and (added 2026-10-27,
see "Sketch support" below) sketch faces built from line / circle
/ arc entities with holes, a face prism, and a face-area query.
Also added 2026-10-27 (see "Selection / query layer" below): a
shape census (face / edge / vertex counts plus per-face and
per-edge info) in the same index space the finishing functions
already consumed. It implements **no CAD
feature logic and no geometry math of its own**: the C++ side only
translates calls and data (handles in, buffers out) and catches
OCCT exceptions at the boundary. Where OCCT has an operation, the
façade wraps it rather than approximating it — e.g. fillets are
`BRepFilletAPI_MakeFillet` (true rolling-ball blends), shell is
`BRepOffsetAPI_MakeThickSolid` (true offset), booleans are
`BRepAlgoAPI_*`.

## OCCT version

- **Open CASCADE Technology 8.0.1** (source release tarball,
  `PACKAGE_VERSION "8.0.1"` in its cmake config).
- Licence: LGPL 2.1 with the OCCT exception. Copies ship at
  `OCCT/LICENSE_LGPL_21.txt` and `OCCT/OCCT_LGPL_EXCEPTION.txt`.

## Subset

The full OCCT tree has 8 modules; this port ships the source of
exactly the toolkits the façade's operations need — the transitive
dependency closure of {TKPrim, TKBO, TKFillet, TKOffset, TKMesh,
TKTopAlgo} computed from OCCT's own per-toolkit `EXTERNLIB.cmake`
dependency declarations:

| Toolkit | .cxx | Role for the port |
| --- | ---: | --- |
| TKernel | 126 (+1 .c) | foundation: memory, exceptions, math base |
| TKMath | 141 | gp geometry, math solvers |
| TKG2d | 42 | 2D geometry |
| TKG3d | 99 | 3D geometry |
| TKGeomBase | 291 | Geom curves/surfaces, adaptors |
| TKBRep | 111 | TopoDS topology, BRep tools |
| TKGeomAlgo | 364 | intersections, projections |
| TKTopAlgo | 156 | BRep builders, classifiers (contains) |
| TKShHealing | 112 | shape healing used by booleans/fillets |
| TKBool | 240 | BOPAlgo boolean engine (low level) |

| TKMesh | 66 (+1 .cpp) | BRepMesh tessellation |
| TKFillet | 114 | BRepFilletAPI fillet/chamfer |

Per-package file selection follows OCCT's own package
`FILES.cmake` lists, plus the package directories' inline include
files (`.lxx` / `.pxx` / `.gxx`) that OCCT collects by glob — the
same set OCCT's cmake build compiles. `GTests` directories (unit
tests, need GoogleTest) are excluded. Totals:

- **2,018 `.cxx` + 1 `.cpp` + 1 `.c` = 2,020 compilable OCCT sources**
  (the `.cpp` is `BRepMesh/delabella.cpp`, the triangulator bundled
  inside OCCT's TKMesh; the `.c` is TKernel's
  `Resource_ConvertUnicode.c`)
- **2,919 header files** in `OCCT/src` (`.hxx/.lxx/.pxx/.gxx/.h`)
- **1 generated header**: `OCCT/generated/Standard_Version.hxx` —
  the only header OCCT generates (from `adm/templates/
  Standard_Version.hxx.in`); the copy shipped here is the exact
  file OCCT's cmake produced for 8.0.1.
- `OCCT/` total: **4,942 files, ~62 MB**.

Excluded modules/toolkits, and why: ApplicationFramework, Data
Exchange (STEP/IGES — TKDE*, TKXCAF, TKXSBase…), Visualization
(TKV3d, TKOpenGl…), Draw, plus the ModelingAlgorithms toolkits
nothing in the closure needs: TKHLR (drawing hidden-line removal),
TKFeat (feature recognition helpers), TKExpress (schema codegen
runtime), TKHelix (OCCT 8's new helical-sweep toolkit — not needed:
threads in MetalCAD are profile sweeps, which `mc_sweep` covers),
TKXMesh (XDE mesh exchange). If a future façade operation needs
one, add its toolkit and its EXTERNLIB closure the same way.

libc++ is linked into the app via `OTHER_LDFLAGS = -lc++`).

Notes from the proof:
- **Circular toolkit references**: TKBool and TKBO reference each
  other (e.g. TKBool's `BRepAlgo_NormalProjection` uses TKBO's
  `BRepAlgoAPI_Section`), so the Linux link wraps the 15 archives
  in `-Wl,--start-group … --end-group`. In the Xcode project all
  objects land in ONE archive (`libCascadeKit.a`) and ld64 rescans
  within a single archive, so no equivalent setting is needed.
- **OCCT 8 API differences** the façade already accounts for
  (found by compiling against the real 8.0.1 headers):
  `TopTools_IndexedMapOfShape` no longer exists — the type is
  `NCollection_IndexedMap<TopoDS_Shape, TopTools_ShapeMapHasher>`;
  symmetric chamfer is `BRepFilletAPI_MakeChamfer::Add(distance,
  edge)` (the old two-distance overload is gone);
  `BRepBndLib::Add` inflates the box by triangulation gap, so
  `mc_bbox` uses `BRepBndLib::AddOptimal` (exact geometry bounds).
- **Shell semantics** (read from the 8.0.1 sources,
  `BRepOffset_MakeOffset::MakeThickSolid`): with an empty
  removed-faces list, `MakeThickSolidByJoin` returns the bare
  inward-offset solid, not the hollow part. `mc_shell` therefore
  composes two OCCT operations — that offset, cut from the original
  with `BRepAlgoAPI_Cut` — both library operations; the façade
  still computes no geometry itself. Result verified: 20×20×10 box,
  1.5 mm walls → exactly 1977 mm³ (4000 − 17×17×7).
- OCCT is built **without TBB** (not present; OCCT parallelises
  internally where compiled in, and every façade call is correct
  single-threaded). TKBO's EXTERNLIB mentions `CSF_TBB` — optional,
  absent here exactly as in OCCT's own no-TBB configuration.
- No resource files are needed at runtime by any façade operation
  (no `CSF_*` environment paths are consulted by these toolkits for
  these calls). This was exercised by the proof run in a bare
  environment.

## Sketch support (added 2026-10-27)

Sean's follow-on ask: sketching must go through Cascade too. Three
façade functions were added; the 20 proof checks below were run
with the same harness (whole suite now **77 checks, ALL PASS** —
the original 57 unchanged):

- `mc_face_from_sketch(origin, normal, xDir, entityTypes,
  entityData, entityCount, profileStarts, profileCount, err)` —
  the sketch plane is a `gp_Pln` (from `gp_Ax3`: origin, normal,
  xDir); each entity becomes a real OCCT curve/edge: lines via
  `GC_MakeSegment`, arcs via `GC_MakeArcOfCircle` on a `gp_Circ`,
  circles as a `gp_Circ` edge, all through
  `BRepBuilderAPI_MakeEdge`; profiles become wires through
  `BRepBuilderAPI_MakeWire` and the face through
  `BRepBuilderAPI_MakeFace(plane, outerWire)` + `Add(holeWire)`.
  Entities arrive as parallel arrays — a type array plus a flat
  data array with a fixed stride of 6 doubles per entity (line:
  x1,y1,x2,y2; circle: cx,cy,r; arc: cx,cy,r,start,end radians
  CCW) — and profiles as CSR ranges (`profileStarts`, count+1
  entries); profile 0 is the outer profile, the rest are holes.
  The result is validated with `BRepCheck_Analyzer` before it is
  handed back, so a bad sketch is an error code, never a bogus
  face.
- `mc_prism_face(face, dir, dist, err)` — `BRepPrimAPI_MakePrism`
  of a face handle (the sketch counterpart of the polygon-only
  `mc_prism`, which stays).
- `mc_face_area(shape, err)` — face area via
  `BRepGProp::SurfaceProperties` (that is OCCT 8.0.1's name for
  the face-properties entry point; its Mass() is the area).

Design note — where the façade's work begins and ends: the plane,
the entities, the wires and the face are OCCT `gp` / `Geom` /
`BRep` objects end to end; **no profile math lives in the
façade**. The only sequencing the façade performs is ordering
each profile's entities end to end (endpoint match within
1e-6 mm) because `BRepBuilderAPI_MakeWire` requires connected
input, plus two pieces of pure representation translation, both
verified empirically against 8.0.1:

- **Hole wires are reversed before `Add`.** OCCT represents a
  hole by a wire oriented opposite to the outer wire, and
  `MakeFace::Add` does not reorient: an unreversed circular hole
  in the proof's 40×40 plate produced area **1678.540** (the hole
  ADDED as material) and failed `BRepCheck`; reversed, the same
  input gives **1521.460** and a valid face. Callers describe
  every profile in the same orientation; the reversal is done
  inside.
- **Arc sweeps are normalised** to CCW from start to end
  (wrapping past 2π); a zero/full-turn sweep is rejected — a full
  circle is the circle entity's job.

## Selection / query layer (added 2026-10-27)

MetalCAD's selection-driven tools (Sean's rule: a tool opened
from a selection uses the selection's actual measurements) need
Swift to enumerate a shape's faces and edges, read their real
geometry, and hand edge indices back to the finishing functions.
Three façade functions were added; the 34 proof checks below were
run with the same harness (whole suite now **111 checks, ALL
PASS** — the original 77 unchanged):

- `mc_shape_counts(shape, *faces, *edges, *vertices, err)` —
  the census: `TopExp::MapShapes` extents for faces, edges,
  vertices.
- `mc_face_info(shape, faceIndex, *area, center[3], normal[3],
  *isPlanar, err)` — area + area centroid via
  `BRepGProp::SurfaceProperties`; planarity + outward normal via
  `BRepAdaptor_Surface` (plane axis, flipped when the face's
  stored orientation is reversed; for a non-planar face the
  normal is reported as (0, 0, 0)).
- `mc_edge_info(shape, edgeIndex, *curveType, *length,
  start[3], end[3], center[3], *radius, err)` — curve type
  (0 line / 1 circle / 2 other) via `BRepAdaptor_Curve`; length
  via `BRepGProp::LinearProperties` (OCCT 8.0.1 has no
  `BRepGProp::EdgeProperties` — LinearProperties is its name for
  the edge entry point, and its Mass() is the length); endpoints
  via `BRep_Tool::Pnt(TopExp::FirstVertex / LastVertex)`;
  circle centre / radius from the adaptor's `Circle()`.

**One index space, by construction.** Faces, edges and vertices
are enumerated in TopExp traversal order (each distinct
sub-shape at its first occurrence — the `TopExp::MapShapes`
enumeration that `mc_edge_count`, tessellation's per-face
ranges, and the finishing functions already used). The census
reads from the same maps, so an index Swift learns from
`mc_edge_info` names the same physical edge in `mc_fillet` —
the proof demonstrates this end to end: the length L0 of edge 0
is read through `mc_edge_info`, edge 0 alone is filleted
through the existing `mc_fillet`, and the resulting volume
matches the closed form for THAT edge to 0.001 mm³.

**No `mc_fillet_edges` / `mc_chamfer_edges` were added** —
`mc_fillet` / `mc_chamfer` already accept an edge index list
(NULL = all edges), implemented by the shared `edgeOp` over the
same map. The selective forms are proven below instead of
duplicated.

Findings from the proof, recorded exactly as measured:

- **Selective finishing is exact.** Box 20×20×10, edge 0
  (L0 = 10, read from the census): fillet r=2 on that edge only
  → volume **3991.416** = 4000 − (2² − π·2²/4)·10, and the
  result has exactly **7 faces**; chamfer d=1 on that edge only
  → **3995.000** = 4000 − (1²/2)·10. Bad indices (face 999,
  edge 999, fillet list {999}) return `MC_ERR_INVALID_ARG`,
  never a crash.
- **The filleted box's true census is 26 / 56 / 24** (faces /
  edges / vertices) — NOT the 72 edges / 48 vertices an earlier
  draft of the test expected. Composition: 6 planar faces
  (areas 256 ×2, 96 ×4) + 12 cylindrical fillet strips (areas
  50.265 ×8 along the 20 mm edges, 18.850 ×4 along the 10 mm
  edges) + 8 spherical corner patches (area 2π each); edges
  are 24 tangent lines + 24 quarter-circle arcs (r=2, length
  π) + **8 degenerate pole edges** (length 0, start == end) —
  one per spherical patch, an artefact of the sphere
  parametrization (each patch is a trimmed sphere face whose
  wire carries a pole edge), not a cell of the decomposition.
  Euler therefore holds on the true cells: V − (E − 8) + F =
  24 − 48 + 26 = **2**. Swift should treat a curveType-2,
  zero-length edge as a pole artefact, not a selectable edge.
- Box census is 6 / 12 / 8 with Euler exact; all 12 edges are
  lines whose lengths sum to exactly 200; all 6 faces are
  planar with areas {200, 200, 200, 200, 400, 400}, and the
  +Z face reports centre (10, 10, 10) and normal (0, 0, 1) —
  the outward-normal orientation convention (reverse on
  `TopAbs_REVERSED`) confirmed empirically on all 6 faces.

## Xcode project

`CascadePort.xcodeproj`, generated by `gen_project.py` in this
repo (deterministic md5 UUIDs; regenerating is byte-identical).

- **CascadeKit** (static library): sources = the 2,020 OCCT files +
  `Facade/occt_facade.cpp`; headers phase = the 2,920 OCCT headers +
  `OCCT/generated/Standard_Version.hxx` + `Facade/occt_facade.h`.
  Settings: C++17 (`gnu++17`), exceptions ON, RTTI ON, the defines
  above, header search paths as above, iOS 17, arm64,
  `TARGETED_DEVICE_FAMILY = 2` (iPad), `SKIP_INSTALL = YES`.
- **CascadeDemo** (app): SwiftUI, bundle `com.user.cascadedemo`,
  display name "Cascade Demo", iOS 17, iPad only, empty
  `DEVELOPMENT_TEAM` (Sean picks his own team in Xcode), links
  `libCascadeKit.a`, façade reached through
  `DemoApp/CascadeDemo-Bridging-Header.h`. The app contains no
  geometry logic: five buttons → façade calls → SceneKit display
  (the fifth is the sketch plate: entities described as Swift
  arrays → `mc_face_from_sketch` → `mc_prism_face` → render).

## Where iOS/Xcode may differ from the Linux proof (honest list)

The first true compile happens in Xcode on Sean's Mac. Known
classes of possible nits, in rough likelihood order:

1. **`__APPLE__` code paths** in OCCT sources that the Linux build
   never took (OSD / resource / signal handling in TKernel). They
   are standard Darwin paths OCCT ships for its own iOS sample, but
   they were not compiled here.
2. **A missing preprocessor define** that Darwin needs and Linux
   didn't (the define set above is exactly the one OCCT's cmake
   used on Linux; OCCT's iOS build script uses the same core set).
3. **Static-initialisation / resource-path behaviour**: OCCT
   registers some factories statically; none of the façade's
   operations needed resources on Linux, but an iOS sandbox path
   difference could surface as an OCCT exception — which the façade
   reports as an error code + message in the demo, not a crash.
4. **Clang vs GCC strictness**: a handful of OCCT files may warn
   (the project does not treat warnings as errors); a hard error
   would be a one-file patch.
5. **The demo's Info.plist** follows the hand-written pattern
   MetalCAD already runs with on-device (no scene manifest); if a
   future iOS demands one, it is a 6-line addition.
